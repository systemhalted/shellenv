Per-project shell sandboxes.

Pin the shell version and option profile a project expects. shellenv exec points HOME, TMPDIR and XDG_* into the project, so writes that go through them stay out of your real home.

Install GitHub

What gets pinned

One script can behave differently across shells. Each project env lives in ./.shellenv/<env>/ and records the conditions it should run under.

Shell runtime
Built from the official source tarball. bash@5.2, bash@3.2.57 and zsh@5.9 are checked against pinned SHA-256 sums; other versions install with a warning.
Option profile
strict (set -euo pipefail), posix or interactive. Fish activation uses a .fish variant; shellenv doesn't install fish.
PATH
The env's bin/ first, then the pinned runtime, then your usual PATH. A tool in bin/ shadows the system copy.
Home and temp dirs
HOME, TMPDIR and the XDG_* config, cache, data and state dirs point into the env's home/. Always with exec; with activate when you pass --isolate-home.

Three ways to run

Each mode puts the env's bin/ first on PATH. They differ in how far the isolation goes. The env is the one you name, else ./.shellenv/current (set by shellenv use), else default.

activate

An interactive session with the env's tools and profile. Leave it with eval "$(shellenv deactivate)", which restores the environment but not shell options the profile set.

Fish pipes it instead:

exec

One-off or scripted runs. Writes through HOME, TMPDIR and XDG_* land in the sandbox, and the exit status passes through. --ephemeral deletes the sandbox home afterwards.

exec --container

For scripts that change the system. Runs in Docker or Podman with the project mounted at the same path. The image supplies the shell, so --strict-shell is rejected.

Know the boundary. Host mode (activate and exec) is a user-space sandbox, not a security sandbox for untrusted code. exec redirects writes that go through HOME, TMPDIR and XDG_*; activate does so only with --isolate-home. The network, processes and the rest of the filesystem stay shared unless you use --container. ARCHITECTURE.md has the details.

Walkthrough

From an empty project directory. Output is from a real run; lines starting with 2> went to stderr.

  1. Create the global home

    A temp SHELLENV_HOME keeps the real ~/.shellenv untouched while you try things.

  2. Declare the shell and profile

    Writes ./.shellenv/default/ with its metadata, bin/ and home/.

  3. Build the runtime

    Until it's installed, commands fall back to the system shell with a warning, or fail with --strict-shell. The build runs once per version.

  4. Run a script under the profile

    --profile sources the strict profile first. Its set -e covers what that shell runs directly, so source the script with .. Run through its own shebang, the script gets a fresh shell and only the profile's exported variables.

  5. Activate, then deactivate

    deactivate restores PATH, the prompt and any isolated variables. It can't undo shell options: after the strict profile, set -euo pipefail and its IFS stay in effect in that shell, so try this in a throwaway one.

Install

A single Go binary for Linux and macOS.

From a release

Download a tarball from the releases page and check it against SHA256SUMS. Replace <version> with the one you downloaded.

  • Keep the binary beside its profiles/ directory, or set SHELLENV_PROFILES to it.
  • Man pages are in man/: man -l man/shellenv.1.

From source

Needs Go 1.22 or later and make.

  • Run from the checkout, it finds the built-in profiles in ./profiles.
  • shellenv install needs a C compiler, make and tar, and takes a few minutes per version. shellenv doctor checks for them.
